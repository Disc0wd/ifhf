Say the name. It asks when it isn't sure.

Type ifhf install spotify and it finds com.spotify.Client for you, shows the app, remote and scope, and asks once before touching anything.

It never guesses. When two apps are equally good matches, as with Firefox in two remotes, you choose. In a script it stops with a distinct exit code and lists the candidates.

--yes is not blind. It refuses fuzzy-only matches, so install terminal will not quietly pick whichever app has “terminal” somewhere in its name.

Removing keeps your data. --delete-data shows a warning, defaults to No, and cannot be switched off in the config.

Why search is so much faster.Flatpak re-reads about 50 MB of AppStream XML on every search. ifhf parses it once into a small index (the first search after deleting it takes @@COLD@@), then answers from memory without starting a process. It also uses @@MEM_IH@@ of memory against Flatpak's @@MEM_FL@@.

Where it still loses.Listing remotes and looking at one installed app wrap a Flatpak call and add their own lookup, such as which apps are installed. That costs 7 to 25 milliseconds, and it is what lets ifhf resolve names and report partial failures exactly. Install, update and remove time is Flatpak's own.

Careful by default.

  • Bypass Flatpak.Signatures, permissions and deployment stay Flatpak's job. ifhf never touches OSTree.
  • Run your input through a shell.Every ID and remote name is validated, and arguments reach Flatpak as separate argv entries.
  • Wait on a closed terminal.Without a terminal on stdin, confirmation needs --yes and the exit code says so.
  • Hide a failed refresh.Unreadable metadata is an error, never an empty catalogue. A failed index rebuild keeps the last good one.
  • Claim atomic installs.When several apps are requested and some fail, it asks Flatpak what is installed and reports exactly which succeeded.
  • Ship untested.Unit, integration and end-to-end tests, including the real binary against a stub Flatpak and a real install and removal in an isolated directory.
